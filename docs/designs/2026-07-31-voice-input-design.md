# Voice Input Design

## Goal

Add a dedicated microphone button to muxterm's mobile title bar that lets users dictate text into the currently-focused terminal pane, using the Web Speech API, following dictation-app UX conventions (tap to start, auto-stop on silence or tap again to stop, transcribed text appears where the cursor is, user reviews and presses Enter themselves).

## Background

Reported by human: "there is NO voice input anywhere?"

## Root Cause

Root-cause investigation (via real execution against `make dev-local` on 127.0.0.1:8313, mobile viewport 390x844) confirmed via `playwright-cli`: xterm.js's hidden `<textarea class="xterm-helper-textarea">` is a completely standard, unrestricted, focusable input (verified via recursive `shadowRoot.activeElement` traversal since muxterm uses Lit shadow DOM components) — nothing suppresses the OS on-screen keyboard. `autocorrect`/`autocapitalize`/`spellcheck` being "off" only affects text correction, not the keyboard's mic/dictation button. Corroborated against external evidence (xterm.js community addon `xterm-addon-edit-context`, whose entire premise assumes native mobile keyboards already appear on xterm's hidden-textarea pattern). SpeechRecognition/webkitSpeechRecognition is supported in Safari 14.5+ iOS and Chrome/Edge everywhere.

Conclusion: this is NOT a broken keyboard. It's a discoverability/trust gap — native OS dictation is an invisible, easy-to-miss feature buried in the system keyboard, and a user reasonably wouldn't consider "an OS feature I stumbled into" the same as "voice input in muxterm." Decision (explicitly approved by user): build a dedicated, visible mic button using the Web Speech API. Do NOT add any discoverability hint/tooltip about native OS dictation — the custom button alone fully addresses the report.

Zero existing voice/speech/microphone code anywhere in the repo — confirmed via grep across the whole tree for `speech|voice|microphone|dictation|webkitSpeech|audio.?input` (case-insensitive), no matches.

## Scope

Mobile web only (narrow layout, `<mux-title-bar>` — rendered per `web/src/lib/breakpoint.ts`'s `isWide()`/`WIDE_MIN_WIDTH = 768` gate). No desktop equivalent in this design.

## Chosen Approach

Singleton controller + thin presentational component. Mirrors this codebase's existing convention for cross-cutting client-side state (`web/src/lib/terminal-registry.ts`, `web/src/lib/pane-focus-coordinator.ts`): a singleton module owns the complex stateful browser API, a thin Lit component only renders UI and delegates to it.

**Rejected alternatives:**

- **Everything inline in title-bar.ts:** title-bar.ts already juggles brand/pane-picker/kebab-menu responsibilities; adding raw SpeechRecognition mechanics inline makes an already multi-concern file bigger and harder to test in isolation.
- **Fully self-contained component** (mic-button owns SpeechRecognition internally, like mux-undo-toast owns its timers): mux-undo-toast's internal state is simple timers, not a genuinely complex external stateful API with permission/event lifecycle. SpeechRecognition deserves the same "own module, subscribable, DOM-independent" treatment already given to terminal-registry/pane-focus-coordinator.

## Architecture

### `web/src/lib/voice-input-controller.ts` (new)

Singleton controller, mirrors terminal-registry.ts/pane-focus-coordinator.ts conventions.

- Feature-detects `window.SpeechRecognition || window.webkitSpeechRecognition` at module load. Exposes `isSupported()`. If neither exists, nothing else in the module does anything.
- State machine: `idle` → `listening` → (`idle` | `error`). No `paused`/`interim` states.
- **Session-token/generation-counter (governs all lifecycle transitions):** the controller holds a single monotonically-incrementing counter. `start()` increments it and captures the resulting value as the new session's token, stored alongside that session's target identity (below) as one immutable record. Every recognition event handler (`result`/`error`/`end`) closes over its own session's token and, on firing, first checks whether that token still equals the controller's current counter value; if not, the handler is a complete no-op — no state transition, no callback invocation — because the event belongs to a superseded session. The controller only transitions back to `idle` (allowing a new `start()`) once it has processed a terminal event (`result`, `error`, or `end` — whichever fires first) for the CURRENT token. This guarantees exactly one active session at a time and prevents a late event from an old, not-yet-fully-torn-down browser-internal session from corrupting a new one (browsers do not guarantee a session is fully torn down the instant `result` fires — `end` can still arrive afterward).
- `start()`: captures a full target identity — BOTH the currently-focused `workspaceId` AND `paneId` (via app.ts's existing pane-focus tracking, reused not duplicated) — since paneIds are workspace-scoped and reused across workspaces (confirmed in `web/src/lib/terminal-registry.ts`'s `_key(paneId)`, which namespaces every paneId lookup by `_currentWorkspaceId`); capturing paneId alone would let a stale target from a previous workspace incorrectly match a same-numbered pane in a new workspace. This identity is stored together with the new session token (above) as that session's immutable record — nothing downstream ever re-reads current focus state to reconstruct it. Requests mic permission implicitly via the SpeechRecognition API (browsers require this triggered by a user gesture — satisfied by the button's click handler), configures recognition with `continuous: false` (native silence-detection auto-stop) and `interimResults: false` (no interim events at all — simplest way to guarantee unfinalized text is never surfaced or acted on).
- `stop()`: calls `recognition.stop()`. No special-cased "auto-stop vs manual-stop" branching — both paths converge on the browser's own `result` (if speech captured) or `end` (if not) events, which the controller handles identically, subject to the token check above. This keeps the state machine simple: exactly one way out of `listening`.
- `invalidateIfActive(target?: { workspaceId, paneId })`: called by external code when the user-visible target is about to change or disappear. Two calling patterns: **with a target** — used for an in-workspace PANE switch (`app.ts`'s pane-select handler), where the new pane's identity IS synchronously known — if the controller currently has a session in flight (`listening`, or between `stop()` and its terminal event) whose stored identity does NOT match the given target, the controller invalidates it. **With no target at all, unconditionally** — used for a WORKSPACE switch (`app.ts`'s workspace-switch handler) and for `mic-button.ts`'s `disconnectedCallback` — any in-flight session is invalidated regardless of its stored identity, with no comparison performed at all. This is not a fallback for when a target happens to be unavailable: the `workspace-switch` event only carries the target `workspaceId`, and the new workspace's pane list/active pane don't exist locally yet at the point invalidation must fire (attachment completes asynchronously after a round-trip) — there is no `newPaneId` to compare against in the first place, and no need to wait for one, since a workspace change definitionally means whatever was being listened for is now stale. General rule, stated once rather than enumerated per call site: any code path that changes which workspace is attached, or forces re-attachment — including paths outside the two named handlers, such as `WorkspaceController.attachWithBreakpoint()` (used for bootstrap/recovery) — must call the unconditional `invalidateIfActive()`, with no argument, before or as part of that change. In either calling pattern, once invalidation applies, the controller immediately calls `recognition.stop()`/`abort()` on the underlying session AND bumps the session-token counter right there, synchronously, before returning — it does not wait for a terminal event. Bumping the counter is what makes invalidation race-safe: any `result`/`error`/`end` the old session still fires afterward — even after a workspace switch completes on its own round-trip — now carries a stale token and is a guaranteed no-op per the token check above, not a best-effort comparison made at delivery time. Transitions to `idle` immediately in all invalidation cases — it does not wait for the stopped session's own events, since those are now guaranteed no-ops.
- Pub/sub: `onStateChange(cb)`, `onTranscript(cb)`, and `onError(cb)` — component subscribes rather than polling.
- On finalized `result` event (token check passes): extracts transcript, notifies via `onTranscript({ text, workspaceId, paneId })` — a single immutable payload carrying the EXACT identity captured at this session's `start()` time, never re-derived from current focus state at delivery time (re-deriving it here would reintroduce the very race this design closes) — transitions back to `idle`.
- On a `SpeechRecognition` `error` event (token check passes; `not-allowed`, `no-speech`, `audio-capture`, `network`, or any other browser-reported error code): transitions to `error` state momentarily then `idle`, ALWAYS calls `onError(message)` with a human-readable message — this is the browser's own explicit signal that something went wrong, and `no-speech` is included here (not treated as a silent case). No retry logic, no exponential backoff — single-shot user-initiated sessions, "tap again" is the retry mechanism.
- On a plain `end` event (token check passes) that fires with NEITHER a preceding `result` NOR a preceding `error` (the distinct, rarer iOS Safari quirk where a session silently terminates with no signal at all): treated as a quiet no-op — no `onError` call, no toast, transitions straight back to `idle`. This is the ONLY case handled this way, and is explicitly distinct from an explicit `no-speech` error event (which always calls `onError`, per above). Explicit YAGNI stance: no other iOS-specific special-casing/workarounds beyond this one distinction, since no other specific iOS quirks have been observed yet in this app — treat unobserved problems as out of scope rather than guessing.

### `web/src/components/mic-button.ts` (new, `<mux-mic-button>`)

Thin Lit component, mounted in title-bar.ts's `.right` container between the pane-picker and the kebab button: `[brand] [pane-picker] [mic] [kebab]`.

- On connect, checks `voiceInputController.isSupported()`. If false, renders nothing at all (not disabled/grayed — fully absent; a visibly broken feature is worse than an absent one).
- Also checks the currently-focused pane's `SurfaceKind` via the existing `isTerminalSurface(kind)` helper in `web/src/types.ts`, called as `isTerminalSurface(pane.surfaceKind ?? 'terminal')`. `SessiondPaneInfo.surfaceKind` (`web/src/types.ts`) is an OPTIONAL field, and the Go backend implicitly treats an omitted value as a normal terminal pane — the common/default case for most panes — so the component normalizes the same way before calling the helper, rather than passing a possibly-`undefined` value straight through (which either fails type-checking, or, if coerced loosely, would incorrectly disable voice input for the majority of ordinary terminal panes whose `surfaceKind` happens to be omitted). `isTerminalSurface` returns true only for `'terminal' | 'driver'`, false for `'browser' | 'settings'`. If the focused pane is NOT a terminal surface (after normalization), OR if there is no focused pane at all (empty workspace, or a transient gap between pane transitions), the button renders DISABLED (greyed out, non-interactive) rather than hidden — the same disabled treatment for both sub-cases, since neither has a valid delivery target. This is deliberately different treatment from the unsupported-browser case: browser support is a fixed, one-time capability check (hide is appropriate), whereas pane focus/kind changes frequently as the user navigates tabs in the mobile single-pane-visible view, so hiding/showing on every tab switch would be visually jarring (a UI element flickering in and out) — disabled-in-place avoids that churn. When disabled for either reason, `aria-label`/`title` explains why (e.g. "Voice input requires a terminal pane"), reusing the same `isTerminalSurface()` helper already in the codebase for consistency rather than inventing a new check.
- Subscribes to controller state; click handler calls `start()`/`stop()`.
- Renders icon/color/pulse based on state (see Visual & UX Spec below).
- On finalized transcript, the controller's `onTranscript` callback delivers a single immutable payload `{ text, workspaceId, paneId }` — the exact identity the controller captured at `start()` time (see Architecture note above). The component forwards this payload VERBATIM as the `detail` of a `voice-transcript` CustomEvent (`bubbles: true, composed: true`, `detail: { text, workspaceId, paneId }`); it does NOT independently track, re-read, or re-derive `workspaceId`/`paneId` from current focus state itself — doing so would reintroduce the same race the captured-identity design is meant to close. Same event-shape convention as this component's existing sibling events `launcher-action`/`workspace-switch`/`pane-select`.
- Subscribes to `controller.onError(cb)` and, on any error callback, triggers a toast (reusing mux-undo-toast's visual styling/positioning/44px-class touch target precedent, NOT its undo-specific button/timeout-to-commit logic) showing the human-readable message the controller provided (e.g. "Microphone access denied," "No speech detected," "Microphone unavailable"). The quiet no-op case (plain `end` with no preceding `result`/`error`) does NOT call `onError`, so no toast fires for it — see Error Handling below for the exact distinction.
- `disconnectedCallback`: calls `voiceInputController.invalidateIfActive()` (no target argument — see Architecture note above; the component itself is disappearing, so there is no successor focus target to compare against, and any in-flight session is invalidated unconditionally). This matters specifically because `<mux-title-bar>` — and this component with it — unmounts entirely on the narrow-to-wide layout breakpoint transition (the title bar only renders in narrow/mobile mode per `breakpoint.ts`'s `isWide()` gate). Without this, the singleton controller could keep an orphaned recognition session running with no visible UI control over it.
- `aria-label` toggles "Start voice input" / "Stop voice input" based on state (matches existing `title="Open menu"` pattern on the kebab button); when disabled for non-terminal pane kind or no focused pane, `aria-label`/`title` instead explains the disabled reason as described above.

### `web/src/components/title-bar.ts` (modified)

Mounts `<mux-mic-button>` as described above.

### `web/src/app.ts` (modified)

Two responsibilities, addressing two different races:

1. **Auto-stop-and-invalidate ownership (new):** `app.ts` already owns the pane-select and workspace-switch event handlers (the mobile pane-picker breadcrumb, and the separate workspace-switch mechanism, respectively). At the very START of each of these existing handlers — BEFORE the switch itself takes effect — the handler now calls `voiceInputController.invalidateIfActive(...)`, with the call shape differing by handler: the pane-select handler passes the target being switched to — `invalidateIfActive({ workspaceId, paneId: newPaneId })` — since the new pane's identity is synchronously known, stopping any in-flight session whose stored identity doesn't match it. The workspace-switch handler instead calls `invalidateIfActive()` with NO target at all, unconditionally, because workspace switches are asynchronous (attachment to the new workspace, including its pane list and active pane, completes only after a round-trip) — there is no new-workspace pane identity available yet at the point this must fire, so there is nothing to compare against and no need to wait for one. Either way, invalidation bumps the session token (see Architecture above) so that any of the old session's events arriving late — even after the switch fully completes — are guaranteed no-ops. This is the actual mechanism that prevents a late `result` from a stale session reaching the terminal; it is not merely a best-effort delivery-time check. This is one instance of the general rule (see Architecture above): any code path that changes which workspace is attached, or forces re-attachment — including paths outside these two handlers, such as `WorkspaceController.attachWithBreakpoint()` used for bootstrap/recovery — must call the unconditional `invalidateIfActive()` before or as part of that change.
2. **Transcript delivery (as before):** listener for `voice-transcript` CustomEvent. Checks whether BOTH `workspaceId` AND `paneId` in the event detail still match the currently-focused workspace and pane (reusing existing pane-focus tracking already used for dockview activation elsewhere in app.ts). Comparing paneId alone is insufficient — paneIds are workspace-scoped and reused across workspaces (see Architecture note above), so a workspaceId+paneId pair that no longer matches on either field must be treated as "the target changed." Given (1) above, a mismatch here should be rare in practice — the controller will already have invalidated and stopped the session before it could produce a transcript against a stale target — so this check remains as defense-in-depth, not the primary invalidation mechanism.
   - If BOTH match: calls the existing `sendPaneInput(paneId, new TextEncoder().encode(text))` API (same wire path real keystrokes already use: `term.onData` → `sendPaneInput` → PTY, confirmed via reading `web/src/lib/terminal-registry.ts` and `web/src/ws.ts` — so transcribed text reaching the PTY is indistinguishable from real typed input). Immediately after `sendPaneInput` succeeds, the handler also explicitly restores DOM focus to that pane's terminal, reusing whatever focus API `web/src/lib/terminal-registry.ts` already exposes for this purpose (the same mechanism used elsewhere when a pane becomes active/focused). This is necessary because tapping the mic button — a toolbar UI element — can take DOM focus away from xterm's hidden textarea; without restoring it, the user's very next physical keystroke (Enter) may not reach the PTY, undermining the "review and press Enter yourself" safety design (Data Flow step 7).
   - If EITHER workspaceId or paneId has changed since listening started: silently discard, no toast, no error — this is expected behavior (see Data Flow / pane-switch below), not a failure.

No backend/Go changes. No changes to terminal-registry.ts or ws.ts themselves — this is entirely a browser-side feature reusing an existing wire path.

`feat/mobile-touch-actions` (a parallel, already-approved but not-yet-coded design being steered in a separate session) will also modify `title-bar.ts`: `:host` height 32px → 44px via `var(--mux-dock-height, 44px)`, and `.launcher-btn` (kebab) 28x24 → 44x44. ## Data Flow

1. User taps `<mux-mic-button>` → component calls `controller.start()`.
2. Controller increments its session-token counter and captures the currently-focused target identity — BOTH `workspaceId` AND `paneId` — as this session's immutable record (token + identity), instantiates/starts SpeechRecognition (`continuous: false`, `interimResults: false`).
3. Controller transitions to `listening`, notifies subscribers → button re-renders (icon swap, color, pulse).
4. On the recognition's `result` event (fires once, since `continuous: false`; passes the session-token check — see Architecture above — meaning no invalidation happened in the meantime): controller extracts final transcript, notifies via `onTranscript({ text, workspaceId, paneId })` — a single immutable payload using the identity captured in step 2 — transitions back to `idle`.
5. `<mux-mic-button>` forwards that payload verbatim as `voice-transcript`'s `detail: { text, workspaceId, paneId }` — it does not re-derive `workspaceId`/`paneId` itself.
6. `app.ts` handler checks if BOTH `workspaceId` and `paneId` (captured at start) still match the currently-focused workspace and pane. If both match: `sendPaneInput(paneId, new TextEncoder().encode(text))`. If either has changed since start: discard silently (no toast/error — expected, not a failure). In practice this mismatch path is defense-in-depth; the primary invalidation happens earlier, at pane/workspace-switch time (see below).
6a. Immediately after that `sendPaneInput` call succeeds, `app.ts` explicitly restores DOM focus to the target terminal pane, reusing whatever focus API `web/src/lib/terminal-registry.ts` already exposes for this purpose (the same mechanism used elsewhere when a pane becomes active/focused). Tapping the mic button — a toolbar UI element — can take DOM focus away from xterm's hidden textarea; without this, the user's next physical keystroke (Enter) might not reach the PTY at all.
7. No trailing Enter ever sent — text lands in terminal input exactly as if typed, cursor after it, user presses Enter themselves. This is a deliberate SAFETY decision, not just a UX preference: unlike a chat box, Enter in a terminal executes arbitrary shell commands, and auto-submitting unreviewed speech-to-text (which can mishear things, e.g. "rm" vs "rn") would be a real hazard.

**Manual stop:** tapping mic again while `listening` calls `controller.stop()` → `recognition.stop()` → browser fires its own `result` (if speech captured) or `end` (if not) — same downstream path as auto-stop-on-silence, no special-cased branching. That event carries the current session's token, still valid, so it's processed normally; the controller only returns to `idle` once that terminal event is processed, not before (see Architecture's session-token rule above).

**Pane-switch mid-listening:** if the user switches to a different pane while listening (via the pane-picker breadcrumb — mobile/narrow layout only ever shows one pane at a time, no splits), `app.ts`'s pane-select handler calls `voiceInputController.invalidateIfActive({ workspaceId: newWorkspaceId, paneId: newPaneId })` at the START of the handler, BEFORE the switch takes effect. If the controller has a session in flight for a different target, this immediately stops the recognition session and bumps its session token, rather than redirecting text to the new pane or locking it to the original pane. Rationale: voice input should always be a "the pane I'm looking at right now" action — redirecting or locking both risk transcribed text landing somewhere the user isn't looking, which is worse than requiring the user to restart dictation on the new pane. Because the token is bumped before the switch completes, any event the old session still fires afterward (a late `result`/`error`/`end`) is a guaranteed no-op per the token check in Architecture above — not just a best-effort delivery-time comparison.

**Workspace switch mid-listening:** switching workspaces entirely (via the separate workspace-switch event/mechanism already in `title-bar.ts`, distinct from the pane-picker's in-workspace pane switching) must trigger auto-stop-and-invalidate, via the same `app.ts`-owned call at the start of the workspace-switch handler — but here the call is `voiceInputController.invalidateIfActive()` with NO target argument, unconditional, rather than a target comparison. This is because the `workspace-switch` event only carries the target `workspaceId`: the new workspace's pane list and active pane don't exist locally yet at the point invalidation must fire (attachment completes asynchronously after a round-trip), so there is no `newPaneId` available to compare against — and no need to wait for one, since a workspace change definitionally means whatever was being listened for is now stale. Both pane-switch and workspace-switch are fundamentally the same event from the user's perspective — "the thing I'm looking at changed" — but they invalidate differently: pane-switch compares against the known new target, workspace-switch invalidates unconditionally. Either way the outcome is identical: invalidate-and-stop, no toast, no error. This same unconditional call is required of any other code path that changes which workspace is attached or forces re-attachment (see Architecture above) — for example `WorkspaceController.attachWithBreakpoint()`, used for bootstrap/recovery, which can change the attached workspace without going through either named handler at all.

**Title-bar unmount mid-listening:** if `<mux-title-bar>` unmounts (the narrow-to-wide layout breakpoint transition, since the title bar only renders in narrow/mobile mode per `breakpoint.ts`), `<mux-mic-button>`'s `disconnectedCallback` invalidates and stops any in-flight session the same way, via `voiceInputController.invalidateIfActive()` called with no target (there is no successor focus target to compare against — the component itself is disappearing — so the controller invalidates unconditionally). Without this, the singleton controller could keep an orphaned recognition session running with no visible UI control over it.

## Error Handling

- **Unsupported browser:** feature-detected once at controller module load; `<mux-mic-button>` renders nothing at all if unsupported (not disabled — absent).
- **Non-terminal focused pane, or no focused pane** (`isTerminalSurface(pane.surfaceKind ?? 'terminal')` returns false, i.e. surface kind is `'browser'` or `'settings'` — noting `surfaceKind` is optional and is normalized to `'terminal'` when omitted, matching the Go backend's own implicit default — OR there is no focused pane at all, e.g. an empty workspace or a transient gap between pane transitions): `<mux-mic-button>` renders DISABLED (greyed out, non-interactive), NOT hidden — distinct from the unsupported-browser case above, and identical treatment for both sub-cases since neither has a valid delivery target. `aria-label`/`title` explains why (e.g. "Voice input requires a terminal pane"). See Architecture / mic-button.ts for full rationale.
- **onError callback contract:** the controller's pub/sub API exposes `onError(cb)`, carrying a human-readable message string, so the component always has a concrete message to show. A `SpeechRecognition` `error` event ALWAYS calls `onError(message)` — this is the browser's own explicit signal that something went wrong.
- **Permission denied** (`error === 'not-allowed'`): controller → idle, calls `onError`, component shows toast "Microphone access denied," button immediately ready for another tap (permission can change in browser settings anytime — never a permanent lockout).
- **Other recognition errors** (`no-speech`, `audio-capture`, `network`, or any other browser-reported error code): same path — controller calls `onError`, component shows a brief human-readable toast (e.g. "No speech detected," "Microphone unavailable"), return to idle. No retry logic — "tap again" is the retry mechanism. Note `no-speech` is included here: it is an explicit `error` event from the browser, not a silent case.
- **iOS silent-end quirk (distinct from `no-speech`):** a plain `end` event that fires with NEITHER a preceding `result` NOR a preceding `error` (the rarer iOS Safari quirk where a session silently terminates with no signal at all) is treated as a quiet no-op return to idle — no `onError` call, no toast. This is the ONLY case handled this way, and must not be conflated with an explicit `no-speech` error event (which always calls `onError` and shows a toast, per above). Explicit YAGNI stance: no other iOS-specific workarounds are built preemptively, since no other specific quirks have been observed in this app yet.
- **Pane-switch or workspace-switch discard:** intentionally NOT treated as an error — no toast, no message, since it's expected behavior. Applies identically whether the target changed via an in-workspace pane switch or a workspace switch (see Data Flow above). Enforced primarily via `app.ts` calling `voiceInputController.invalidateIfActive(...)` before the switch takes effect (stopping and invalidating any in-flight session via the session-token bump), with the delivery-time identity check in the `voice-transcript` handler as defense-in-depth only — see Data Flow above for the full mechanism.
- **Title-bar unmount mid-listening:** also NOT treated as an error. `<mux-mic-button>`'s `disconnectedCallback` calls `voiceInputController.invalidateIfActive()` unconditionally (no target to compare against, since the component is disappearing) to stop and invalidate any in-flight session — otherwise an orphaned session could keep running with no visible UI control over it. See Data Flow above.

## Visual & UX Spec

- **Placement:** title bar `.right` container, between pane-picker and kebab: `[brand] [pane-picker] [mic] [kebab]`.
- **Sizing:** 44x44px touch target via `var(--mux-dock-height, 44px)`-based convention (coordinated with feat/mobile-touch-actions, see cross-branch note above) — NOT the current on-disk 28x24px kebab size.
- **Idle state:** `Mic` icon (Lucide, via existing `icon()` helper in `web/src/lib/icons.ts`) at 16-18px (matching kebab's icon sizing), `color: var(--chrome-text-bright)`, transparent background, `:hover` uses `var(--chrome-hover)` — identical interaction pattern to `.launcher-btn`.
- **Listening state:** icon swaps to a stop/mic-off-style affordance (e.g. Lucide `MicOff` or similar), background/icon color shifts to a distinct accent (`var(--chrome-accent)` or a dedicated theme token if one exists for "recording" state — reuse existing tokens from `web/src/lib/theme.ts`'s `applyChromeTokens()`, never hardcode colors), plus a subtle CSS pulse animation (opacity or box-shadow glow oscillating, ~1.5s ease-in-out infinite). No text label — icon + color + motion is sufficient (Siri/Assistant-style convention). Deliberately NO interim transcript preview (rejected — iOS Safari doesn't reliably fire interim results the way Chrome does, and this adds complexity for marginal value).
- **Error/toast:** reuses `mux-undo-toast`'s visual styling/positioning/44px touch-target precedent (see `web/src/components/mux-undo-toast.ts:52-56`), not its undo-specific logic — simple auto-dismissing message.
- **Disabled state (non-terminal pane, or no focused pane):** standard disabled-button convention (greyed out, non-interactive), distinct from the fully-hidden unsupported-browser case — see Architecture / mic-button.ts for rationale. Re-evaluated on every focus change, since pane focus/kind can change frequently as the user navigates tabs.
- **No persistent visual difference across pane switches** — button is global chrome, not per-pane; resets to idle on pane-switch (or workspace-switch) auto-stop-and-invalidate, same as manual stop.
- **Accessibility:** `aria-label` "Start voice input" / "Stop voice input" toggling by state; "Voice input requires a terminal pane" when disabled for non-terminal pane kind or no focused pane.

## Verification Approach

Per this repo's AGENTS.md: NO UNIT TESTS (banned). Verification is real execution only, using `make dev-local` on 127.0.0.1:8313 (never touching production on 8311), with a fresh workspace/pane for every verification run (per AGENTS.md's "Verification hygiene" section).

**What real-execution verification CAN prove:**

- **Rendering/placement/sizing:** `playwright-cli` at a real mobile viewport (390x844 confirmed working), snapshot to verify mic button exists in title bar at correct position, confirm 44x44px bounding box.
- **Click → permission request → listening state:** using Chromium's fake/synthetic media stream support (`--use-fake-device-for-media-stream` or CDP permission grants) if `playwright-cli` exposes it, or by programmatically granting mic permission — verify button transitions to the visually-distinct listening state (icon/color/pulse) without requiring a human to grant a real permission dialog.
- **DEV-only test accessor (the concrete seam):** the previous plan to "dispatch a synthetic result event directly at the controller's registered handler" has no actual seam to attach to — the controller is a module-private singleton with no accessor exposed to a browser-automation tool like `playwright-cli`'s `page.evaluate()`. Fix: follow the SAME established pattern already in this codebase — `web/src/lib/terminal-registry.ts` exposes a `window.__muxterm` DEV-accessor object (e.g. `window.__muxterm.snapshot`) for exactly this purpose. `voice-input-controller.ts` extends that SAME `window.__muxterm` object (not a separate global) with a narrowly-scoped `window.__muxterm.voiceInput` accessor exposing exactly three operations, chosen because the invalidation/staleness test this design exists to enable (see below) requires all three: (1) **start** a session and read back the session-token it was assigned, so a test can capture that token for later use; (2) **invalidate** the active session (simulating a pane/workspace switch — the same `invalidateIfActive()` path production code calls); (3) **inject** a synthetic `result`/`error`/`end` event tagged with an EXPLICITLY SPECIFIED token argument — which may be a previously-captured, now-stale token from operation (1), not necessarily whatever token is currently active — routed through the real session-token check from Architecture above, so an injected event carrying a stale/invalidated token is correctly a no-op, same as production. "Inject into the controller's current session" cannot express the staleness test at all, since the whole point of that test is to inject for a session that is, by definition, no longer current; requiring an explicit token argument is what makes the test expressible while still exercising the real production gate rather than a separate bypass path. A read of the controller's current state (`idle`/`listening`/`error`) and its in-flight session's target identity is also exposed, needed to observe the effect of (1) and (2). This is the only DEV-mode surface added, and it is additive to the existing `__muxterm` object rather than a new global.
- **Transcript delivery to the terminal:** since real microphone/speech input can't be exercised headlessly, drive this via `page.evaluate()` calling `window.__muxterm.voiceInput`'s start operation to begin a session and capture its token, then its inject operation to deliver a synthetic `result` event — tagged with that just-captured token — carrying a known fake transcript string, then verify that exact string appears in the terminal's actual pane content (via DOM inspection, same shadowRoot-traversal technique used in root-cause investigation) — proving the full pipeline (event → controller → `onTranscript` → `voice-transcript` CustomEvent → app.ts → `sendPaneInput` → PTY → back to terminal display) works end-to-end, with synthetic input standing in for a real voice through a real, executable accessor rather than an unspecified direct handler call.
