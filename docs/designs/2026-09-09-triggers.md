# Triggers: schedules and file watches that spawn lanes

Status: implemented (this branch)
Scope: the smallest trigger that is genuinely useful, and a written list of what
was deliberately left out.

The ask was "can we easily add a cron-styled or file-watch trigger". The answer
is yes, because muxterm already owns every hard part except *deciding when*.
This document is mostly about what was NOT built, and why the safety half is
larger than the scheduling half.

---

## 1. Prior art (read before designing)

Two repositories were read end to end. Both exist, both were readable, and both
changed this design.

### microsoft/amplifier-drumbeat -- "scheduled automations using Amplifier Agent"

Python. Time-triggered agent automations against pinned, resumable Amplifier
sessions.

- **Schedules are free text**, not cron: `every N minutes|hours` and
  `daily at HH:MM` only (`scheduler.py:69-92`). The daily form was added only
  after a real unmet need proved it -- explicit YAGNI, recorded in the code.
- **A run** submits a turn to a pinned session and persists `result.json` with
  `run_id/failed/notified/error` (`runner.py:273-296`).
- **Overlap is not prevented per automation.** The whole scheduler tick is one
  sequential loop (`scheduler.py:507-618`); a slow run delays everything behind
  it. Measured result: ~412 runs/day demanded, ~127 completed -- 31%.
  What they *did* guard, after it bit them in production, is two scheduler
  *processes* double-firing, via an `flock` single-instance lock
  (`scheduler.py:293-339`).
- **Missed fires are skipped, never caught up** (`scheduler.py:172-217`), capped
  at one missed day, "never run late and never queued".
- **No auto-disable after N failures.** Their own words: "recording-brief failed
  10 runs in a row"; and "a dead, log-only automation stayed dead for 27 hours
  because nothing pushed its failure anywhere".
- **Approval gates were considered and explicitly rejected**
  (`docs/AUTOMATIONS.md:846-847`): "the engine runs unattended, so an approval
  block is a silent no-op." That single line shaped section 6 below.
- The deepest lesson is about *silence*, not runaway cost.
  `test_crash_visible_notify_runs.py:2-8` records that a crashed run produced
  `notified: false` -- **byte-identical** to a healthy run that decided nothing
  was worth reporting.
- **No file-watch trigger at all.** An `event` trigger type is declared in the
  schema and nothing dispatches it.

### kenotron-ms/amplifier-app-loom -- "cross-platform scheduled job daemon"

Go. Closest structural sibling: a daemon, a bbolt store, a web UI.

- `robfig/cron/v3` with seconds enabled, plus a `loop` duration form and a
  `once` form (`scheduler.go:40-43,131`). No explicit timezone handling.
- **Overlap prevention exists**: `sync.Map` `LoadOrStore` keyed by job id
  (`queue.go:34-48`) -- but a skip is only `slog.Warn`ed, never recorded. A
  `RunStatusSkipped` constant exists in the enum with no write site.
- **Missed fires: absent.** Nothing computes "should have fired at X".
- **File watch**: 300ms debounce (`watcher.go:30`), recursive opt-in, SHA-256
  content diffing to reject mtime-only editor touches. **No default ignore
  list** and **no watch-descriptor limit handling** -- `addWatchPaths` walks and
  `w.Add`s every directory it finds (`watcher.go:335-352`).
- **No auto-disable after failures.** Concurrency cap `maxParallel`, default 4.
- **Abandoned, and this is the most valuable line in either repo**: they built
  and then ripped out an xterm.js-in-browser terminal-hosting layer in favour of
  launching native terminals and reading the agent's own on-disk session store.
  Reason given: "over-solving... native terminals handle terminal emulation
  better than any web-based approach can"
  (`docs/plans/2026-04-13-loom-redesign-design.md:9`).

### What the prior art changed here

| Their gap | What this design does |
|---|---|
| loom skips overlaps but doesn't record them | every skip is a persisted fire record with a reason |
| neither auto-disables a failing job | disable after 3 consecutive failures, with the reason stored |
| loom watches with no ignore list | ignore list on by default; ignored dirs are never even walked |
| loom ignores inotify limits | hard cap on watched dirs; **refuse to create** rather than half-watch |
| drumbeat: silence is indistinguishable from success | "never fired", "fired and produced nothing", and "skipped" are three different records |
| loom: don't reimplement what the host does well | a trigger spawns a lane; it executes nothing itself |

## 2. What a trigger does: it spawns a lane. Only that.

A trigger's action is exactly `spawn_lane`'s: resolve-or-create a workspace,
open a pane, launch `amplifier` or `claude` in it with a prompt or a goal.

This is the whole design. Everything else follows, because a lane already has:

- a **lifecycle** -- a pane, a process, an exit;
- a **declared state** -- `working|blocked|done|failed|stopped`, which is what
  overlap prevention consults;
- a **durable result** -- a `CompletionRecord` written by the pane-exit path
  whether the lane succeeded, crashed, or was killed (`completion.go`);
- **visibility** -- a fleet row and a card in the home view;
- **teardown** -- closing the workspace.

A trigger that spawns a lane inherits all five for free. That is why this is a
small feature and not a platform.

### Rejected: sending input to an existing session

Requires a live session that may not exist at fire time, and -- fatally -- gives
a "run" no boundary. You cannot tell when a keystroke's consequences finished,
so you cannot prevent the next fire from overlapping it. Section 6 is not
implementable on top of this, which rules it out on its own.

### Rejected: running a bare shell command

Two variants, both bad:

- *Headless* means muxterm grows a run executor -- output capture, exit codes,
  timeouts, a log store, a second lifecycle beside the pane one. This is
  precisely the layer loom deleted.
- *In a pane* is just an unlabelled lane that declares nothing and produces no
  verdict.

There is also a standing argument in this repo for the visible variant only: the
chief of staff's bundle grants `run_command` (runs in a pane a human can watch,
scroll and interrupt) and withholds `bash` (runs invisibly), and says why at
length in `internal/cos/sidecar/bundle/behaviors/muxterm-cos.yaml`. A trigger
firing at 3am with no human present makes that argument stronger, not weaker.

### One action type, on purpose

"Easily" argues for one. A second action type would double the surface of every
subsequent decision -- overlap, audit, failure-disable, the MCP schema -- and buy
nothing `spawn_lane` does not already do.

## 3. Where it lives: inside the daemon

The scheduler is a goroutine in `sessiond`, the long-lived daemon.

- `sessiond` is the **only** always-running process. It already owns the
  workspace registry and pane lifecycle, already persists across restarts
  (`restore-snapshot.json`, `completions.json`), and already computes the
  session-state rows overlap prevention needs.
- The `muxterm mcp` process is a short-lived **client** of sessiond; it exits
  when the agent's conversation ends. A scheduler there would stop scheduling
  the moment the user closed a chat.
- Drumbeat's `flock` lesson comes free: sessiond is already single-instance per
  socket, so two schedulers cannot double-fire.

### What external cron/systemd timers would have saved, and cost

Genuinely saved: all of section 4. No cron parser, no tick loop, no missed-fire
policy -- `systemd.timer` even has `Persistent=true` for catch-up.

Cost, and why it loses anyway:

1. The schedule lives in a file muxterm cannot see, so section 7 becomes "go
   read `/etc/cron.d`". That defeats the point.
2. **Overlap prevention would still have to be written.** A lane outlives the
   command that spawned it, so `systemd`'s own "don't start if still running"
   guard watches the wrong process entirely.
3. There is no cron equivalent for file watching. `systemd.path` units are
   per-path, do not debounce, and do not recurse.
4. muxterm ships cross-platform; this would be Linux-only in practice.
5. The chief of staff could not create or manage a trigger, and acting on the
   user's behalf is its entire job.

## 4. Schedules

**Format: standard 5-field cron**, parsed by `robfig/cron/v3`'s
`cron.ParseStandard`. The library's *parser* is used; its scheduler is not --
this code drives its own ticker, because it must own skipping, capping and
auditing, and a library that "just runs the func" cannot express any of those.

One field accepts both idioms a human reaches for:

```
0 9 * * 1-5        weekdays at 09:00
*/15 * * * *       every quarter hour
@every 30s         interval form
@daily @hourly     descriptors
CRON_TZ=America/Los_Angeles 0 9 * * *
```

`@every` is why there is no separate interval type: one field, one parser, both
idioms, no second format to document or validate.

**Timezone: the machine's local time by default.** A human who writes `0 9 * * *`
means 9am where they are, not 9am UTC. `CRON_TZ=` overrides per trigger. DST is
handled by `time.Location` arithmetic inside the parser, which means the usual
consequences are inherited and are the ones a cron user already expects: on a
spring-forward day a 02:30 daily fire does not happen, and on fall-back it does
not fire twice (`Next` advances strictly).

**A fire missed because muxterm was down is missed. It is never run late.**

Both prior arts behave this way and drumbeat states it outright. Catch-up after
an overnight outage produces a stampede: an `@every 5m` trigger down for eight
hours would owe 96 lanes at startup, each of which costs money. On startup the
next fire is computed from *now*, so at most one occurrence is lost. This is
written in the tool description, not only here, because silently doing one while
a user assumes the other is the actual failure mode.

## 5. File watches

`fsnotify`, recursive from the watched root.

**Debounce: 2s.** Loom uses 300ms, and 300ms is right *for loom*, whose runs are
shell commands. A fire here launches an AI coding agent that makes commits and
costs money, so the quiet window is longer on purpose: a burst of events
coalesces into exactly one fire, and the cost of waiting an extra second and a
half is nil. A single editor save emits several events (write, chmod, rename of
a temp file); a build emits thousands.

**Ignores, on by default**, because loom not having them is the named gap:

```
.git  node_modules  .venv  venv  __pycache__  target  dist  build
.next  vendor  .idea  .vscode  .mypy_cache  .pytest_cache  .tox
```

plus editor scratch files (`*.swp`, `*.swx`, `*~`, `.DS_Store`, `4913`,
and dotfile-prefixed temporaries). Ignored directories are **skipped during the
walk**, so they never consume a watch descriptor -- watching a repo without this
both buries you in events and pins a CPU.

**Recursion and limits.** Watches are recursive. `inotify` has a per-user cap
(`fs.inotify.max_user_watches`) and exhausting it breaks *other software on the
machine*, not just muxterm. So the walk counts directories and stops at
**2000**, and a tree that exceeds it causes `create_trigger` to **fail** with the
count and the cap named.

Refusing is the deliberate choice over half-watching: a partially-watched tree is
a trigger that silently never fires for half its paths, which is
indistinguishable from a trigger that is broken. Fail at create time, in front of
a human, rather than at 3am in a log nobody reads.

## 6. Safety

This feature creates work with no human in the loop. It is the largest section
because it is the part that can cost money while the user sleeps.

Note what is *not* here: an approval gate. Drumbeat considered and rejected one
in exactly this position -- "the engine runs unattended, so an approval block is
a silent no-op" -- and that reasoning holds. The safety model is therefore
*prevention and cheap stopping*, not consent.

### Overlap prevention

Before firing, the trigger's previous lane is checked. If its pane still exists
and its session has **not** declared a terminal state (`done`, `failed`,
`stopped`), the fire is **skipped** and a `skipped-overlap` record is written.

Both halves are needed. Pane-existence alone is wrong now that a finished
`/goal` loop resumes interactively in the same pane -- the pane outlives the
work, so a pane-only check would wedge the trigger forever. Session state alone
is wrong because a lane that has not yet declared anything has no row.
An undeclared lane whose pane is alive counts as **still running**: the
conservative direction is always "do not start another".

### Caps

- **3 concurrent trigger-spawned lanes**, globally, across all triggers. The
  fourth fire is skipped and recorded. Triggers are not the only thing spawning
  lanes on this machine and they should not be able to crowd out the human.
- **`max_runs` per trigger**, optional, default 0 (unlimited). On reaching it the
  trigger disables itself and records why.

### Failure-disable

**After 3 consecutive failed runs the trigger disables itself** and stores the
reason, which `list_triggers` shows. A run counts as failed when its lane's
completion record says `failed`.

This is the one guardrail both prior arts lack and both paid for. A trigger
firing every five minutes into a lane that dies on startup is a loop that burns
money for hours; drumbeat watched exactly that happen ten times in a row.

Three, not one: a flaky network or a transient provider error should not
permanently disable a working trigger. A success anywhere in the run resets the
counter to zero.

### Surviving a restart, and the bug that only running it found

The store is durable, so triggers and their fire logs survive. The thing that
does **not** survive is the meaning of a workspace or pane id.

Observed live: a trigger's lane ran in `w3 pane 1`; the daemon restarted; the
restore pass rebuilt the workspaces in a different order and `w3 pane 1` came
back as an unrelated lane belonging to a *different* trigger. The overlap check
found a live pane at those coordinates and skipped every subsequent fire. A
schedule trigger wedged indefinitely by a stranger, with a skip reason that read
perfectly plausibly.

`completionFor` was already safe -- it requires `EndedAt >= LastFireAt`, which is
exactly what `mergeCompletionRows`' warning about recycled ids demands. The
pane-existence half of `laneRunning` had no equivalent. So on startup, any
last-lane coordinates with no durable completion behind them are forgotten, and
the unaccounted run is written to the fire log as `orphaned`.

The direction is deliberate and it is the one place this design does *not* pick
the conservative-looking option. A lane whose daemon died before writing a
completion record will never get one, so treating it as still-running is not
conservative, it is permanent: the trigger never fires again and waiting does
not help. Forgetting fires at most one extra lane, once, and the overlap check
covers everything after it. A recoverable wrong beats an unrecoverable one.

Related, and left alone: muxterm's existing restore feature re-runs a pane's
command on restart, so a triggered lane that was mid-flight comes back and runs
again. That is the restore contract for every pane, not something triggers
should special-case, but it is worth knowing that a restart can cost one extra
lane run through a door that has nothing to do with scheduling.

### Disable and delete

`set_trigger_enabled(id, false)` and `delete_trigger(id)`. Both take effect
immediately -- the scheduler re-reads the store each tick and the watcher checks
`enabled` at fire time, so neither waits for a restart, and a delete tears down
its `fsnotify` watches with it. Neither touches lanes already spawned: stopping
the trigger is not the same gesture as killing the work, and conflating them
would make "stop firing" a destructive action nobody wants to reach for quickly.

### Audit trail

Every fire *attempt* appends a record: `fired`, `skipped-overlap`,
`skipped-cap`, `skipped-max-runs`, or `error`, with a timestamp, the reason, and
the workspace and pane it spawned. Bounded to 20 per trigger.

This is drumbeat's crash-visibility lesson applied directly. "Fired three times
overnight and produced nothing", "was skipped three times because the first lane
never finished", and "never fired at all" are three completely different
problems, and without records they are one indistinguishable silence.

## 7. Visibility

Four MCP tools, all prefixed `mcp_muxterm_`:

- `create_trigger` -- kind, schedule-or-path, and the lane to spawn
- `list_triggers` -- id, kind, schedule, enabled, last fire, **next fire**,
  run/failure counts, disabled reason, and recent fire history
- `set_trigger_enabled` -- the stop button
- `delete_trigger`

`list_triggers` is deliberately fat rather than splitting history into a fifth
tool: the question a human actually asks is "what is set up and has it been
working", and that should be one call.

### Three of the four are withheld inside a pane

A lane is an autonomous agent with a shell. A lane that can call
`create_trigger` can arrange for **more lanes, on a schedule, indefinitely**,
with no human ever having asked -- self-perpetuating unattended work, which is
the exact thing every safeguard above exists to bound. `delete_trigger` destroys
a human's configured automation, and `set_trigger_enabled` can re-arm one a
human deliberately turned off.

So a server running inside a muxterm pane gets `list_triggers` and nothing else.
That is the same guard `close_workspace` and `close_pane` already sit behind, and
the same principle: withhold reach that STARTS OR STOPS things, not reach.
`list_triggers` destroys nothing and answers a question a lane has real reason to
ask -- is something else about to fire into this repository while I work in it.

### The chief of staff

It keeps all four, because it is a sidecar of `muxterm serve` rather than a pane
process -- the same real coupling `spawn_lane`'s registration comment already
names. Managing the human's automations on their behalf is its job.

It reaches them through the `mcp_muxterm_*` prefix in its allowlist, so nothing
had to be added there. Its **charter** -- the prose it reads as a system prompt --
is what changed, because a tool an agent has not been told about is a tool it
does not use, whatever the allowlist says. The charter carries the rules
unattended work needs: propose a trigger rather than install one, prefer disable
to delete, read the fire log before answering "did it run", and treat
`disabled_reason` as the answer to "why did my automation stop".

A triggers applet is a follow-on, not part of this change. Two sibling branches
are editing the applet registry concurrently and the conflict cost is real,
while the information itself is already reachable.

## 8. Deliberately not built

Named so nobody has to guess whether they were forgotten.

- **Webhook / HTTP-triggered runs.** Out of scope.
- **Git-event triggers** (push, PR). GitHub Actions already does this.
- **Triggers on remote machines.** The machine-scoped tools exist and this would
  follow their pattern; it is the natural second step after the applet.
- **Chaining** -- a trigger that fires when another lane completes. This is the
  obvious next want, and `CompletionRecord` is already the event it would
  subscribe to.
- **Conditions, expression languages, retry policies** beyond the
  failure-disable above.
- **Catch-up firing** after downtime. Section 4; a decision, not an omission.
- **Content hashing** to reject mtime-only touches (loom does this). The 2s
  debounce plus the ignore list handles the observed noise; hashing a tree on
  every burst is real cost for a case not yet seen here.
- **Per-trigger concurrency > 1.** A trigger runs one lane at a time, full stop.

## 9. Evidence

Run against an isolated daemon: its own `XDG_RUNTIME_DIR` and `XDG_DATA_HOME`,
its own Unix socket, no TCP port, and a stub `amplifier` on `PATH` so the spawn
path is exercised end to end without spending anything on a real agent. The
production instance was untouched throughout.

| Claim | How it was shown |
|---|---|
| a cron trigger fires on schedule and spawns a lane | `@every 20s` created at T; fired at exactly the `next_fire_at` predicted at creation; workspace `trigger-evidence` created, pane 1 opened, harness exec'd with `run "<prompt>" --mode chat` |
| **overlap prevention skips a fire while the previous lane works** | lane sleeps 60s; four scheduled fires occurred; log reads `fired`, then three `skipped-overlap` each with a reason; exactly ONE process actually started |
| the skip is temporary, not a wedge | when the lane ended, the next scheduled fire ran normally |
| a file-watch trigger fires on a real change | writing under the watched tree fired it and spawned a lane |
| **debounce coalesces a burst** | 60 writes plus 3 ignored files in ~3ms produced exactly ONE fire, ~2s after the burst |
| ignores are skipped during the walk | a tree with `.git`, `.git/objects`, `node_modules`, `node_modules/pkg` and `src` was watched as **2 directories** |
| the watch cap refuses rather than half-watching | a 2002-directory tree was rejected at create time with a message naming inotify and saying what to do instead |
| triggers survive a restart | both survived with state and fire history; the watch re-established its watches at startup |
| a missed fire is missed | after the restart the schedule was armed for exactly one interval from *now* -- no backlog |
| disable takes effect | disabled mid-run; over 48s (>2 intervals) no new fire records and no new processes; `next_fire_at` gone |
| delete takes effect | both deleted; `list_triggers` returned 0 |

The restart run is also what produced section 6's recycled-id bug. It was not
visible from reading the code, and it is the reason this section exists.
