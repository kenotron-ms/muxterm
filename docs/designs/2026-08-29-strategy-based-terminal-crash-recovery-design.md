# Strategy-Based Terminal Crash Recovery Design

## Outcome

Muxterm absorbs the behavioral capabilities of tmux-resurrect and tmux-continuum into sessiond core. Sessiond records authoritative mutations and lifecycle transitions as they occur, without polling, and automatically reconstructs workspaces and terminals after sessiond death, controlled replacement, or host reboot.

Recovery is reconstructive, not process or PTY resurrection. The latest committed workspace structure, pane identities, membership, layout, titles, active selection, dimensions, surface metadata, validated working directories, and bounded terminal history return first. Every restored pane then has a fresh usable default shell in its saved working directory; selected programs recover independently through constrained core strategies.

The initial strategy support contract includes, in settled product-priority and reference order: amplifier-app-cli, Claude Code, OpenCode, and Codex. All four must capture an exact durable session identity, survive daemon or host-style loss, and resume that exact conversation before muxterm claims strategy-based crash recovery. This order establishes product priority and the reference adapter; it is not a partial-release sequence.

## Scope and Non-goals

In scope are sessiond-owned write-through structural persistence, an event-driven mutation journal, compacted state snapshots, bounded terminal-history segments, automatic cold-start reconstruction, process and working-directory evidence, a constrained strategy registry, non-destructive lifecycle integrations, the four required product strategies, controlled daemon replacement, and daemon-authoritative browser recovery states.

Live browser or web-server loss remains a reattachment case: the existing sessiond, PTYs, and processes continue and no reconstruction occurs. Sessiond loss and host reboot are reconstruction cases: structure and selected durable tool conversations return in new processes.

Unknown or unselected programs are never replayed. Their panes return as fresh usable shells in validated saved working directories, matching tmux-resurrect behavior. Program recovery is best-effort and pane-scoped; structure, layout, history, and the shell remain useful when a strategy cannot recover.

Out of scope are process memory restoration, PTY descriptor resurrection, shell variables and jobs, in-flight pipelines or tool calls, automatic repetition of interrupted prompts or side effects, arbitrary command replay, terminal-display parsing as identity evidence, selection of a “latest” session, browser-owned snapshots, external recovery plugins, polling-based state discovery, ambient environment or credential persistence, and lossless capture of the final terminal-output tail.

## Evidence and Constraints

- Core tmux preserves live PTYs only while its server survives. Its server death and a host reboot lose those sessions.
- Tmux-resurrect reconstructs structure as shells first, reapplies layout and selection, and then restores only selected programs through per-program strategies. Unknown programs remain usable shells. Recovery merges without duplicating existing state and failure is isolated per pane.
- Tmux-continuum polls and invokes external save and startup restore behavior only because it sits outside the authoritative server. Sessiond already owns every relevant mutation and lifecycle transition, so core persistence is event-driven instead.
- Structural changes acknowledged to users must survive an immediate crash. The durable commit therefore precedes in-memory publication, authoritative broadcasts, and success acknowledgement.
- Terminal output is high-volume and may be coalesced; structural truth and tool-session identity cannot. Output-tail loss must have an explicit measured bound.
- Sessiond is the sole authority for structure, persistence, strategy selection, launch claims, and recovery outcomes. The browser presents state and user intent only.
- Amplifier persists project-scoped transcript, event, and metadata state under a full stable identifier, but its current interactive startup identity channel is weaker than the other required tools.
- Claude Code and Codex expose authoritative lifecycle evidence with stable session identity and working-directory context. OpenCode exposes managed session, status, and event evidence; unmanaged interactive selection is not sufficient identity proof.
- A resumed tool restores only its own last durable conversation checkpoint. Completed external effects may precede that checkpoint, and an in-flight operation cannot be inferred or repeated safely.
- Durable recovery state and terminal history are sensitive owner data. Only minimal allowlisted launch context may be retained.
- Verification uses fresh real browsers, real sessiond processes, real shells, and real tool processes. New unit tests are prohibited; compiler and type gates support but do not replace end-to-end evidence.

## Decisions

| ID | Decision | Rationale | Ranked alternatives |
|---|---|---|---|
| D-01 | Adopt the tmux-resurrect and tmux-continuum behavioral model as an automatic sessiond-core capability, while replacing their polling and unsafe shell mechanisms. | Core ownership provides stronger durability and automation without external plugins or a manual restore prerequisite. | 1. Selected: behavioral fidelity with stronger core mechanisms; 2. literal shell-script compatibility; 3. managed-agent-only recovery that leaves ordinary panes blocked. |
| D-02 | Persist through an event-driven write-ahead mutation journal, compacted state snapshots, and bounded terminal-history segments. Compaction follows journal size, event-count, or clean lifecycle boundaries, never a state-polling timer. | The journal preserves every acknowledged mutation, snapshots bound replay cost, and separate history segments prevent high-volume output from dominating structural truth. | 1. Selected: journal, compaction, and bounded segments; 2. rewrite one complete atomic generation after every mutation; 3. Continuum-style interval polling, rejected because sessiond owns the events. |
| D-03 | Serialize each structural mutation as validation, durable journal commit, deterministic in-memory application, authoritative broadcast, then success acknowledgement. Persistence failure rejects the mutation before it becomes visible or successful. | This is the minimum consistency contract under which an acknowledged workspace or pane change survives an immediate crash. | 1. Selected: synchronous durable structural commit; 2. publish then persist asynchronously; 3. periodic snapshots with an acknowledged-loss window. |
| D-04 | Journal workspace and pane creation, closure, rename, membership, layout, active selection, dimensions, and surface metadata from the mutation boundary. Record process start and exit, working-directory changes, tool-session capture, strategy-relevant lifecycle transitions, and recovery outcomes from their authoritative events. | Sessiond can record facts at the moment they become authoritative rather than infer them later. | 1. Selected: event-bound records; 2. periodic process and state scans; 3. browser-generated snapshots. |
| D-05 | Feed terminal output into bounded append segments, coalesced by size and elapsed output time, and flush at structural or lifecycle boundaries and clean shutdown. | Output persistence stays affordable while crash loss is limited to a declared tail and never threatens structural durability. | 1. Selected: arrival-driven bounded segments; 2. synchronous persistence per output byte; 3. full-buffer polling snapshots. |
| D-06 | On cold startup, load the latest valid compacted snapshot, replay committed journal records, reconstruct shells, structure, layout, selection, dimensions, titles, and available history, then launch selected program recovery. Ignore torn tails and preserve the latest prior valid state. | Structure-first recovery returns a coherent usable workspace before optional program recovery and bounds corruption impact. | 1. Selected: automatic structure-first replay; 2. manual restore; 3. automatic structure with confirmation required for every program. |
| D-07 | Start every restored pane as the configured default shell in its validated saved working directory. Apply selected strategies only after that shell-backed pane exists. Unknown and unselected programs remain shells and are not replayed. | This matches Resurrect’s safe and useful fallback while guaranteeing every pane remains usable. | 1. Selected: shells plus safe allowlisted strategies; 2. opt-in strategies only; 3. replay every captured command, rejected as unsafe. |
| D-08 | Use a built-in constrained strategy registry with product adapters and a non-destructive integration manager. Built-in and future user strategies share one contract: capture identity, determine selection, produce structured executable and argument data, and validate the resumed identity; they never emit shell text, replay terminal input, or enable unrestricted restore-all behavior. | A common secure contract isolates product semantics without hard-coding them into reconstruction. Omitting tmux-resurrect’s dangerous unrestricted restore-all escape hatch is a deliberate safety improvement. | 1. Selected: constrained core registry; 2. external plugin scripts; 3. product branches embedded in the coordinator. |
| D-09 | Treat amplifier-app-cli, Claude Code, OpenCode, and Codex as one required initial support roster, in that product-priority and reference order. No strategy-based crash-recovery claim is valid until all four pass acceptance. | The roster is table stakes, and amplifier-app-cli defines the reference quality bar rather than becoming an optional later adapter. | 1. Selected: all four in one support contract; 2. partial product support; 3. generic command recovery without product guarantees. |
| D-10 | Make amplifier-app-cli the reference strategy. Capture its full stable identifier and working-directory namespace through authoritative lifecycle integration when available; otherwise accept project-store correlation only when pane start identity, namespace, creation or update window, and candidate set prove exactly one full identifier. | Exact identity enables seamless durable conversation recovery while ambiguity fails closed. | 1. Selected: authoritative capture or uniquely proved correlation; 2. parse terminal display text; 3. choose continue or latest, rejected as unsafe. |
| D-11 | Use Claude Code’s authoritative lifecycle evidence to bind stable session identity, transcript identity, working directory, and startup or resume source to the pane, then resume only that exact session. | The lifecycle contract provides direct identity evidence without storage guessing. | 1. Selected: lifecycle-bound exact identity; 2. infer from recently changed transcripts; 3. interactive recent-session selection. |
| D-12 | Use OpenCode’s managed session, status, and event evidence to bind a stable session identity and recorded directory. Automatic recovery is allowed only when that identity was authoritatively captured. | Managed evidence can prove the intended conversation; unmanaged interactive selection cannot. | 1. Selected: managed exact-session capture; 2. require explicit recovery for every OpenCode pane; 3. guess from recent sessions. |
| D-13 | Use Codex’s authoritative session-start lifecycle evidence to bind stable UUID, transcript identity, working directory, and startup or resume source, then resume only that exact UUID. Never infer identity from stored transcript names or last-session selection. | The lifecycle callback is stronger and safer than filesystem heuristics. | 1. Selected: lifecycle-bound exact UUID; 2. infer from transcript naming; 3. select the last session. |
| D-14 | Install or activate muxterm-owned namespaced lifecycle callbacks non-destructively where supported, preserve user integrations, record integration health, and refuse automatic recovery when capture is stale, absent, conflicting, or ambiguous. | Integration ownership must not clobber user configuration or turn uncertain evidence into launch authority. | 1. Selected: namespaced cooperative integration; 2. overwrite tool configuration; 3. rely on terminal parsing. |
| D-15 | Define tool recovery as exact durable conversation resumption in the last validated working directory. Never repeat an interrupted prompt or claim restoration of in-flight work. Show a compact recovery boundary because external side effects may precede the last tool record. | Conversation continuity is achievable; execution continuity is not. | 1. Selected: exact durable session with explicit boundary; 2. replay the last turn; 3. imply complete process continuity. |
| D-16 | Mark strategy launch as recovered only after authoritative post-launch evidence matches the captured session where available. Otherwise retain a visibly provisional outcome rather than substituting another session. | Launch success alone does not prove that the intended conversation opened. | 1. Selected: post-launch identity validation or provisional status; 2. trust launch arguments; 3. accept any resumed session. |
| D-17 | Recover panes independently and idempotently per recovery generation. Persist claim, attempt, and outcome before launch; bound transient readiness checks; prevent restart from duplicating a claimed launch; and permit retry of a failed attempt only through explicit user intent. | Pane isolation preserves best-effort recovery and durable claims remove Continuum’s duplicate-start window. | 1. Selected: persisted generation claims; 2. process-presence heuristics; 3. automatic retry until success. |
| D-18 | Store recovery data as owner-only sensitive state, validate schema, ownership, working directory, executable identity, session identity, and argument fields, and retain only minimal allowlisted environment deltas. Never persist ambient credentials. | Journal and strategy records cross a command-execution boundary and expose terminal and project context. | 1. Selected: least-authority structured records; 2. broad encrypted process snapshots; 3. raw command strings and full environments. |
| D-19 | Use the same recovery path for controlled daemon replacement. Replacement proceeds only after a committed generation and only when every active pane has a valid selected strategy or the user explicitly accepts shell-only reconstruction; otherwise the old daemon remains live and replacement is deferred. | Recovery capability is not permission to destroy unrecoverable live work. | 1. Selected: eligibility-gated replacement; 2. always replace and recover best-effort; 3. never replace a running daemon. |
| D-20 | Project restoring, recovered, shell restored, selection needed, provisional, and strategy failed as daemon-authoritative states. Browsers render them but do not select strategies or own persistence. | Every client must converge on one recovery truth and cannot inspect authoritative process or tool state. | 1. Selected: daemon authority and browser projection; 2. browser-led recovery; 3. independent per-client decisions. |

The dominant tradeoff is deliberate: synchronous structural durability adds mutation latency and disk writes in exchange for truthful crash survival. High-volume terminal output is coalesced separately so this guarantee does not require synchronous byte-level persistence. Complexity is concentrated in one daemon-owned durability boundary and constrained product adapters; security and reliability take precedence over unrestricted replay compatibility.

## Components and Boundaries

| Component | Owns | Does not own | Expected file or subsystem boundary |
|---|---|---|---|
| Sessiond mutation transaction boundary | Structural validation, serialization, durable-before-visible ordering, deterministic application, broadcast, and acknowledgement | Terminal-output batching, product semantics, or browser rendering | Daemon mutation authority boundary |
| Durable journal and snapshot store | Owner-only journal records, snapshot compaction, schema and integrity validation, replay, retention, and prior-valid rollback | Process launch, UI state, or terminal rendering | Daemon durability boundary |
| Bounded terminal-history checkpoint service | Arrival-driven buffering, immutable bounded segments, flush boundaries, retention, integrity, and tail-loss accounting | Structural acknowledgement, shell input replay, or tool conversation authority | Terminal state persistence boundary |
| Workspace and pane reconstruction coordinator | Structure-first restore, merge without duplication, shell creation, layout and selection application, and per-pane recovery state | Product-specific identity semantics or browser policy | Daemon reconstruction boundary |
| Process and working-directory evidence service | Pane-qualified process generations, start and exit evidence, working-directory changes, and strategy-relevant lifecycle facts | Strategy policy, durable publication, or recovery claims | Daemon process-evidence boundary |
| Strategy registry and integration manager | Strategy selection, adapter contracts, schema compatibility, lifecycle integration health, structured launch validation, and exact-session outcomes | Workspace mutation authority or product-owned conversation storage | Core recovery-strategy boundary |
| Amplifier strategy | Full identifier capture, working-directory namespace binding, uniquely proved fallback correlation, exact-session recovery, and validation | Latest-session selection or restoration of process-local modes, provider pins, goals, environment, or prior bundle contents | Product recovery adapter boundary |
| Claude Code strategy | Lifecycle-bound stable identity, transcript and directory binding, exact-session recovery, and validation | Background or in-flight tool restoration | Product recovery adapter boundary |
| OpenCode strategy | Managed session and event identity, recorded directory binding, exact-session recovery, and validation | Guessing unmanaged interactive selection | Product recovery adapter boundary |
| Codex strategy | Lifecycle-bound stable UUID, transcript and directory binding, exact-session recovery, and validation | Transcript-name inference or last-session selection | Product recovery adapter boundary |
| Controlled daemon replacement coordinator | Durable readiness census, compatibility decision, shell-only consent, replacement authorization, and defer state | Strategy internals or forced termination of ineligible live work | Service lifecycle boundary |
| Browser recovery-state projection | Rendering authoritative recovery boundaries and pane-scoped statuses, plus explicit selection or retry intent | Persistence, strategy selection, identity validation, or launch authority | Client presentation boundary |

## Interfaces and Flow

| Flow | Authoritative input | Durability and control semantics | Result |
|---|---|---|---|
| Structural mutation | Validated workspace or pane intent | Commit a generation-qualified journal record before in-memory application, broadcast, and acknowledgement | An acknowledged change survives an immediate crash; a persistence failure produces no visible mutation. |
| Terminal output | Pane-qualified output arrival | Append to a bounded buffer and flush immutable segments on size, elapsed-output, structural, lifecycle, or clean-shutdown boundaries; never scan for changes | Useful history survives with a measurable bounded tail-loss window. |
| Tool identity capture | Pane-qualified lifecycle callback and process evidence | Validate integration health, product identity, working-directory binding, and session identity before committing a strategy capture record | Only exact or uniquely proved identities become automatic recovery authority. |
| Compaction | Journal size, committed event count, or clean lifecycle boundary | Publish a complete integrity-checked snapshot before retiring covered journal and history records | Replay cost and storage remain bounded without polling authoritative state. |
| Cold startup | Latest valid snapshot, committed journal prefix, valid history segments, and current compatibility evidence | Ignore torn tails, replay deterministic records, merge by stable identity, and reconstruct shells, structure, layout, selection, dimensions, titles, and history before program recovery | The browser receives a coherent usable workspace before optional strategy outcomes. |
| Selected program recovery | Durable strategy identity, validated working directory, current integration health, and unclaimed recovery generation | Commit the claim and attempt, launch from structured executable and argument data, then compare observed exact-session evidence | The pane becomes recovered, provisional, selection needed, or strategy failed without affecting other panes. |
| Unknown or unselected program | Saved pane and working-directory evidence without an eligible strategy | Perform no program replay and preserve only shell, structure, metadata, and history | The pane is a usable shell with shell-restored status. |
| Strategy ambiguity or failure | Missing, stale, conflicting, unsupported, or mismatched evidence | Preserve the reconstructed shell and history, commit the pane-scoped outcome, and require explicit user intent for selection or retry | No guessed session, duplicate side effect, or workspace-wide rollback occurs. |
| Controlled replacement | Committed readiness census for every active pane | Authorize replacement only when every pane is strategy-recoverable or explicitly accepted as shell-only; otherwise keep the old daemon authoritative | Replacement and ordinary cold recovery share one contract, while unsafe upgrades defer. |

## Failure Handling

| Failure | Required behavior | Blast radius and recovery path |
|---|---|---|
| Disk full, unsafe ownership, permission denial, or durable-commit failure during a structural mutation | Reject before application, broadcast, or success acknowledgement and retain the prior authoritative state. | The attempted mutation alone fails; live panes and the prior committed generation remain authoritative. |
| Torn journal tail | Stop at the last integrity-valid committed record and ignore the incomplete tail. | At most the unacknowledged tail is lost; prior structure remains usable. |
| Interrupted or corrupt compaction | Ignore the unpublished snapshot and replay from the previous valid snapshot and committed journal. | Compaction work is discarded without replacing valid authority. |
| Corrupt pane, history, or strategy record | Quarantine only the invalid scope and reconstruct every independently valid workspace, pane, and history segment. | The affected pane degrades to a usable shell or a visible failure state; unrelated panes continue. |
| Missing or invalid saved working directory | Open a shell only in the configured safe default with a visible warning; never auto-resume a managed tool into a different directory. | One pane loses directory fidelity and requires user resolution. |
| Missing executable, credentials, compatible tool state, or transcript | Do not launch or choose another session; preserve shell, history, and a pane-scoped recovery status. | Other strategies and panes continue independently. |
| Missing, stale, conflicting, or ambiguous session identity | Never select latest. Leave the shell usable and report selection needed or integration unavailable. | One managed pane requires explicit resolution. |
| Lifecycle callback configuration conflict | Preserve user configuration, decline automatic identity capture, and report integration health as unavailable. | Existing user hooks continue; affected panes cannot claim seamless automatic recovery. |
| Exact-session validation mismatch after launch | Stop only the new recovery process, retain the shell and history, and commit strategy failure. | No substitute conversation is accepted; explicit retry or selection is required. |
| Crash after recovery claim but before confirmed outcome | Treat the persisted claim as consumed and do not launch it automatically again. | Duplicate selected programs are prevented; explicit retry remains available. |
| Tool startup does not become ready within its bounded checks | End the claimed attempt as strategy failed without starting another automatic attempt. | The pane remains a usable shell and explicit retry remains available. |
| Tool state trails an externally completed side effect | Resume only the last durable conversation, display the compact recovery boundary, and never repeat the interrupted action. | Uncertainty is visible and no automatic duplicate side effect occurs. |
| Output segment not yet flushed at crash | Lose no more than the declared tail bound and mark the recovered history boundary accordingly. | Structure and tool-owned conversation state remain intact. |
| Controlled replacement finds an unrecoverable active pane or cannot commit readiness | Leave the old daemon and all live PTYs untouched and report deferred replacement. | No partial replacement or silent data loss occurs. |

## Verification Outcomes

| Outcome | Observable evidence | Acceptance signal |
|---|---|---|
| Browser or web-server crash | An active terminal and selected tool continue under the same live sessiond and reappear in a fresh real browser. | No reconstruction, process replacement, or duplicate strategy launch occurs. |
| Sessiond death | A forced daemon loss is followed by automatic startup using only durable muxterm and tool state. | Exact workspace and pane identities, membership, layout, titles, selection, dimensions, working directories, bounded history, and statuses return. |
| Host-style fresh boot | All muxterm processes are absent before startup while durable recovery and tool stores remain. | Automatic reconstruction succeeds without claiming prior process or PTY continuity. |
| Immediate structural crash durability | A crash is forced immediately after acknowledgement of each structural mutation category. | Every acknowledged mutation reappears exactly once; no unacknowledged mutation becomes visible. |
| Structural persistence failure | Durable writes are made to fail during a mutation. | No success acknowledgement, authoritative broadcast, or phantom post-restart mutation occurs. |
| Output-tail bound | Output is produced continuously and the daemon is killed at varied points before coalesced flush. | Measured loss never exceeds the declared bound and the browser visibly marks the recovered boundary. |
| Idle shell recovery | A real idle shell is reconstructed after daemon and host-style loss. | A fresh process opens in the validated saved working directory with restored structure and history. |
| Unknown side-effecting program | An unselected program creates an observable side effect before loss. | Recovery creates no second side effect and leaves a usable shell in the saved directory. |
| Amplifier exact-session recovery | A real amplifier-app-cli conversation exposes or uniquely proves one full identifier, then survives daemon and host-style loss. | The same durable conversation resumes in the same working-directory namespace; no interrupted turn is repeated. |
| Amplifier ambiguity | Multiple plausible project-scoped sessions satisfy incomplete evidence. | No automatic launch occurs; the shell remains usable with selection-needed status. |
| Claude Code exact-session recovery | A real lifecycle-captured conversation is interrupted and reconstructed. | Post-launch evidence matches the exact captured session and directory before recovered is shown. |
| OpenCode exact-session recovery | A real managed session is captured and reconstructed; a separate unmanaged interactive session is also exercised. | The managed exact session resumes; the unmanaged session is never guessed or auto-resumed. |
| Codex exact-session recovery | A real lifecycle-captured conversation is interrupted and reconstructed. | The exact captured UUID and saved directory validate; no last-session fallback or interrupted-turn replay occurs. |
| Required roster contract | All four product strategies run the same daemon-loss and host-style acceptance matrix. | Strategy-based crash recovery is advertised only when every product passes exact identity, directory, and no-repeat checks. |
| Missing dependencies | Saved working directory, executable, credentials, or tool transcript is independently removed. | Failure remains pane-scoped; shell, structure, and history remain usable, and no alternate session opens. |
| Corruption isolation | Torn tails, interrupted compaction, and individual corrupt pane, strategy, and history records are injected separately. | The latest prior valid state loads and unrelated panes recover normally. |
| Recovery idempotence | Sessiond is restarted repeatedly during and after strategy launch claims. | At most one automatic recovery launch occurs per pane and recovery generation. |
| Controlled replacement allowed | Every active pane has a valid strategy or accepted shell-only reconstruction and readiness is durably committed. | Replacement completes through the same automatic recovery path and exact outcomes converge in the browser. |
| Controlled replacement deferred | At least one active pane is neither strategy-recoverable nor accepted as shell-only. | The original daemon and PTYs remain live and replacement reports a redacted defer reason. |
| Integration preservation | Existing user lifecycle integrations coexist with muxterm-owned namespaced callbacks and a deliberate conflict is introduced. | Compatible integrations remain unchanged; conflicts disable only muxterm capture and do not overwrite user configuration. |
| End-to-end discipline | Every scenario uses fresh workspaces and real browsers, daemons, shells, and tool processes; compiler and type gates run on the same state. | No mock, newly added unit test, or static-only assertion substitutes for observed recovery behavior. |

## Assumptions and Risks

| ID | Assumption or risk | Consequence if false | Containment |
|---|---|---|---|
| R-01 | External lifecycle, persistence, and exact-session resume contracts remain compatible with recorded strategy versions. | A tool upgrade could make a prior capture unresumable or ambiguous. | Version strategy records, continuously validate integration health, and fail to a shell rather than guess. |
| R-02 | Amplifier’s startup identity channel remains weaker until a documented machine-readable lifecycle callback exists. | Unique disk correlation may not prove every interactive session, preventing universal seamless recovery. | Require exactly one full identifier under strict pane, namespace, and time evidence; ambiguity becomes selection needed. |
| R-03 | Tool-owned data may not be power-loss durable through its final record. | The recovered conversation can trail what the user last saw. | Display a recovery boundary and treat only validated durable tool state as conversation authority. |
| R-04 | External side effects can complete before the corresponding durable tool record. | Repeating an apparently incomplete turn could duplicate destructive work. | Never repeat interrupted prompts or in-flight actions automatically. |
| R-05 | Working directories, executables, credentials, compatible versions, and session stores remain available. | Exact-session recovery can fail despite intact muxterm structure. | Validate each dependency independently and preserve a usable shell with pane-scoped status. |
| R-06 | Terminal history and external session metadata may contain sensitive data. | Recovery storage or logs could expose secrets, projects, or conversation identity. | Enforce owner-only storage, minimize environment capture, redact identifiers, bound retention, and never treat history as input. |
| R-07 | Synchronous durable structural commits add acceptable latency and disk wear. | Interactive mutations may feel slower or storage may wear faster. | Keep records compact, compact by bounded event thresholds, and batch only nonstructural history writes. |
| R-08 | Journal growth and interrupted compaction remain within strict replay and storage bounds. | Startup can slow or storage can grow without limit. | Bound retained generations and segments, trigger compaction by size and event count, and retain a prior valid snapshot until publication completes. |
| R-09 | Recovery claims remain durable across repeated daemon failures. | A selected program could launch more than once after crash loops. | Commit claim and outcome before launch transitions and require explicit retry after an interrupted claim. |
| R-10 | Namespaced callback installation can coexist with user tool configuration. | Automatic identity capture may be unavailable for some installations. | Preserve user configuration, expose integration health, and fail closed to shell-only recovery. |
| R-11 | Terminal-output coalescing can provide a stable and measurable loss bound across supported storage. | Recovered visual history may omit more context than promised. | Define conservative segment thresholds, flush on authoritative boundaries, measure acceptance on each supported environment, and surface truncation. |
