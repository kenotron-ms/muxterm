## F4 — the three safety properties, on the merged tree

The evidence below was captured on `629231b`, the rebased branch head. The merge was a
merge commit, so the shipped tree could in principle differ from the verified one. It
does not:

```

verified branch : f434214bc071a9dccd17a9a2fc3a30d283b1cd16
IDENTICAL
```

Two independent lines of evidence: a mechanical diff of route protection, and a runtime
harness driving the real `Server` in **production posture** — `BehindReverseProxy: true`,
which disables the loopback auth bypass exactly as the live instance's
`behind_reverse_proxy = true` does.

### Property 1 — the bypass is scoped to the publish prefix ONLY · PASS

Mechanically, over the whole route table:

```
main:   22 protected, 7 anonymous
merged: 26 protected, 9 anonymous

--- routes PROTECTED on main and NOT protected on merged (must be empty) ---
--- (end) ---

--- NEW anonymous routes on merged vs main ---
s.mux.HandleFunc("GET /p/_asset/doc.js", s.handlePublicAsset)
s.mux.HandleFunc("GET /p/{id}", s.handlePublicDocument)
```

Nothing lost protection. The four new owner routes are all wrapped in `protect()`
(`internal/server/server.go:260-263`); the static catch-all is still wrapped
(`server.go:286`); and #106 does not touch the auth middleware at all — its
`internal/server` diff is confined to `publish.go`, `publish_api.go`, `publish_css.go`
and the registrations in `server.go`.

The bypass is by REGISTRATION, not by a conditional — there is no flag, header or
request-derived condition that can promote a protected pattern into an unprotected one
(`server.go:207-222`). Both public patterns are fixed-shape, so no caller-controlled
component reaches the filesystem.

At runtime, every route requested with no `Authorization` header, with `StaticFS`
deliberately holding the string `THE APP BUNDLE` so a leak would show as a 200:

```
  REFUSED  /                                -> 503
  REFUSED  /index.html                      -> 503
  REFUSED  /ws                              -> 503
  REFUSED  /api/config                      -> 503
  REFUSED  /api/files                       -> 503
  REFUSED  /api/prs                         -> 503
  REFUSED  /api/tunnels                     -> 503
  REFUSED  /api/publications                -> 503
  REFUSED  /api/remotes                     -> 503
  REFUSED  /api/update/status               -> 503
  REFUSED  /api/ai/status                   -> 503
  REFUSED  /api/cos/voice/trace             -> 503
  REFUSED  /t/abc/                          -> 503
  SERVED   /api/health                      -> 200  {"status":"ok"}
  REFUSED  /p/AAAAAAAAAAAAAAAAAAAAAA        -> 404
  REFUSED  /p/_asset/doc.js                 -> 404
```

503 is the middleware failing closed; the handler never runs. On the same server
config a real `/p/{id}` returns 200 with content (P2, read 1) — so the contrast is
exact: the publish route serves anonymously, every other route does not.

### Property 2 — pinned by inode, re-validated on EVERY read · PASS

The pin is device+inode, not name (`publish.go:206-213`), captured at publish
(`publish.go:294-309`). Every read goes `handlePublicDocument` → `readPinned`
(`publish_api.go:134`) → `openPinned` (`publish.go:605`), whose own comment reads
"Called on EVERY read, never once at publish." `openPinned` compares dev/ino against
the pin and refuses (`publish.go:615`). `openPinnedPath` (`publish.go:574`) opens with
`syscall.O_NOFOLLOW`, and before that `ensureNoSymlinkComponents` (`publish.go:541`)
walks **every** component with `os.Lstat` and refuses any symlink — closing the
directory-swap attack `O_NOFOLLOW` alone does not cover. The caller receives an open
fd, so the check-to-read window is closed.

Three attacks, run against the real handler:

```
  published .../note.txt  pinned dev=224 ino=763596
  read 1 (untouched)                    -> 200  "ORIGINAL CONTENT"
  read 2 (file -> symlink to secret)    -> 409  "This link is broken: the file it points to is not the file that was published, so nothing was served."
  read 3 (same name, NEW inode)         -> 409  "This link is broken: ..."
  read 4 (dir case, untouched)          -> 200  "DIR-ORIGINAL"
  read 5 (PARENT DIR -> symlink)        -> 409  "This link is broken: ..."
```

The secret's bytes never appeared in any response. Replacing the file, or a directory
component of its path, with a symlink produces a REFUSAL, not the new target.

### Property 3 — every publication carries a TTL; revocation is immediate · PASS

```
  ttl omitted        -> expires_at=2026-09-09T23:38:57Z (default 24h0m0s, not forever)
  ttl 720h (>cap 168h0m0s) -> refused: ttl 720h0m0s exceeds the maximum of 168h0m0s for a public link
  before expiry      -> 200  "TTL-CONTENT"
  after expiry       -> 410  "This link has expired. It stopped working at 2026-09-08T23:38:59Z."
  before revoke      -> 200
  Revoke()=true, NEXT request -> 404  "This link is not valid."
  Cache-Control on a live publication: "no-store, no-cache, must-revalidate, private"
```

No code path creates a publication without an expiry: `Create` substitutes the 24h
default for 0 and rejects anything over the 7-day cap rather than clamping
(`publish.go:271-280`). Revocation is immediate because nothing is copied at publish
and every public response is `no-store` (`publish_api.go:224-228`). The registry is
in-memory by design, so a restart revokes everything — the fail-closed direction
(`publish.go:243-247`).

The harness was a throwaway file, used to produce the output above and then deleted.
It is not part of the merge.
