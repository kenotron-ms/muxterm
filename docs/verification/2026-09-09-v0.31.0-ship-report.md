### Deploy method

muxterm's own upgrade machinery under `internal/update`, driven through the owner-only
`POST /api/update/apply` route, rather than a hand-rolled stop-and-start. That path verifies the
GoReleaser checksum before installing, renames atomically on the same filesystem, and — because
`[restore] enabled = true` in the config — restarts `muxterm-sessiond.service` and `muxterm.service`
together so systemd's `After=` ordering holds and the daemon is never left version-skewed under a
newer web process.

The running server already sees the release:

```
$ curl -H "Authorization: Bearer <local token>" http://127.0.0.1:9090/api/update/status
{"currentVersion":"0.30.0","latestVersion":"0.31.0","updateAvailable":true,
 "canUpdate":true,"devBuild":false,"method":"binary"}
```

### The Amplifier hook has to move too, and that is the gentler mechanism

This release is the first where the binary alone is **not** enough. The Go side carries a `Todo`
field that only `modules/hooks-muxterm-session` ever populates, and that module is installed into
Amplifier from `git+…/muxterm@main#subdirectory=modules/hooks-muxterm-session`. The local bundle
cache is pinned well behind main:

```
$ cat ~/.amplifier/cache/muxterm-*/.amplifier_cache_meta.json
{"ref":"main","commit":"994f07b49870f2d02f15fb697410b9447a2022d6","cached_at":"2026-09-09T03:08:36"}
   994f07b = "docs: v0.29.0 ship report" — two releases old
```

So a card would stay blank forever with a perfectly healthy new binary. The fix is the repository's
own documented command, `muxterm amplifier install`, which is `amplifier bundle add --app` followed by
an explicit `amplifier bundle update muxterm --yes` — and `main.go:844` explains at length that the
refresh half exists precisely because "upgrading muxterm, re-running `muxterm amplifier install`, and
getting a hook from weeks ago with no error to explain why the home view reports nothing" is the
observed silent-failure shape. That existing mechanism is used, rather than anything hand-rolled.

## S6 — after the restart

Deliberately not in this commit. The restart terminates the pane this lane runs in, so the deploy and
the post-restart checks are handed to a **detached transient systemd unit** — its own cgroup, so it
survives `systemctl --user restart muxterm-sessiond.service`, which a plain `setsid` would not (the
whole unit cgroup is signalled). That unit applies the update, waits, runs the health checks
(version, `/proc/<pid>/exe` with no `(deleted)`, socket present on disk, a **fresh client dial**,
`/proc/net/unix` consistency, web response), refreshes the Amplifier hook, proves the feature with a
real session that keeps a todo list and one that does not, rolls back if the instance does not come
back, and commits the result as a follow-up.
