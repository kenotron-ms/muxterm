Read this first

None of this is a picture of what the car will look like. Android Auto apps do not draw. They hand the head unit a template — a structured object — and the head unit renders it in its own styling. The fonts, the colours, the spacing, the row height, the header chrome, the scroll behaviour: all of it belongs to the manufacturer, and it differs between a Pixel-tethered Android Auto session and a built-in Automotive OS car.

So the screens below are faithful to the structure and approximate about everything else. Tick Show what the host controls above to see the line. What is inside the green is yours to decide. What is outside it is not, and no amount of design work will make it yours.

D1 · The template

Chosen: ListTemplate with two SectionedItemLists. It is the only general-purpose template that gives two labelled groups of rows on one screen with no navigation, which is exactly the shape of the requirement: two short lists, one screen, no drill-down.

Two sections in one template are possible — this was worth checking, because the rich Section header component is documented as exclusive to the newer Sectioned Item template. Plain sublist headers on ListTemplate are a different, older thing: ListTemplate.Builder.addSectionedList() has existed since 1.0.0 and rejects an empty header, and the List template design page lists “Include a section header when sections are present” as a MUST. So NEEDS MY INPUT and ONGOING can be two headed groups in one list.

RejectedWhat it would have cost
PaneTemplate Content limit of 4 rows against the list's 6, and rows in a pane cannot be clicked (ROW_CONSTRAINTS_PANE sets setOnClickListenerAllowed(false)) — so no tap target for voice inside the body. Built for one static block of detail, not a changing fleet.
GridTemplate A grid item is an image with a short label. Our payload is two lines of prose per lane (“Run brew upgrade on the Mac, then say go”). A grid would either drop that text or shrink it to nothing.
MessageTemplate One message, up to 2 actions. It could state “3 lanes working, 1 blocked” and nothing else — you would lose which lane and what it wants, which is the entire content.
TabTemplate Puts blocked and working on separate tabs, so the blocked lane is invisible until you tap — exactly the thing you look at the screen to avoid. It also replaces the header with tabs, which removes the action strip, which removes voice option A.
SectionedItemTemplate The genuinely better fit on paper: richer section headers, and it is the only template that supports Banners. But it is newer (Car App Library 1.9-era) and raises the minimum host API for no capability this screen needs. Worth revisiting if you ever want a banner.
Anything map-based Gated behind the NAVIGATION / POI / WEATHER categories, and would put a map on screen that this app has no use for.

D2 · The states

Six states, drawn with voice option A (the action-strip button). The same six with option B are further down. Every screen obeys the same row budget: 6 rows, the library's fallback for getContentLimit(CONTENT_LIMIT_TYPE_LIST). Real hosts may allow more; none allow fewer.

1 · The common case

Nothing blocked, three lanes working. What it teaches: when nothing needs you, the screen should look calm and finish in one glance. The NEEDS MY INPUT section is not rendered at all — an empty section is illegal (addSectionedList throws on an empty list), and an empty heading would read as a fault.

2 · One lane blocked — the reason you looked

What it teaches: the blocked lane has to be the first thing your eye lands on, and it has to say what it wants without you tapping. The section header does that work: it is fixed text at the top, above everything else. Position, not colour, carries the priority — because colour is not ours (D4).

3 · Overflow — more lanes than rows

Four blocked and seven working against a 6-row budget. What it teaches: the split is not even. Blocked takes as many rows as it needs up to 5, working keeps at least one row so you can still tell that work is happening, and each section that overflows spends its last slot on a counting row. There is no scrolling to design for here — a driver will not scroll, and the host may stop them.

4 · Nothing running — the empty state

What it teaches: an empty list with two headings and no rows looks broken, so there are no headings at all — one plain sentence instead. This is also the state you see most often, because most of the time nothing is running.

Voice — three ways, two of them real

Voice is the interaction; the screen is only a glance surface. So the live/not-live state has to be unmistakable, and the control has to be one tap. The template gives three places to put it, and you cannot have the first and the third at the same time — the design guidance says not to put an action strip and a floating action button on the same template. Mocked all three; pick one.

Option A — action-strip button (drawn above)

  • Yes: it is the only control on this template that may carry a word. One label button is allowed per action strip. TALK / LISTENING is unmistakable without colour.
  • No: it is small, it sits top-right in the header, and it costs a template step to change if the host does not support app-driven refresh — the action strip is not row content, so it falls outside the refresh rule's list of things you may change for free.
  • Also: ListTemplate.Builder.setActionStrip() is deprecated as of Car App Library 1.7.0 in favour of Header.Builder.addEndHeaderAction(). Same control, newer spelling — but it means option A is the one that has already moved once.

Option B — a pinned voice row

The row title stays the fixed word Voice and the state lives in the secondary text. That makes it the only option whose state changes are free under the refresh rule (D3) — secondary text is the one thing you may change without spending a step. It costs one of the 6 rows, so the fleet budget drops to 5.

Option C — floating action button

Drawn so it can be rejected on sight. A FAB is icon-only and must carry a background colour — the API refuses one without both an icon and a background CarColor. It is the biggest, easiest target on the screen and the worst at saying what it is doing, because it can say nothing at all. It also excludes the action strip, and ListTemplate.Builder.addAction() requires Car API 6 — the same floor as app-driven refresh.

D3 · Overflow and truncation

The row budget

Ask the host: constraintManager.getContentLimit(ConstraintManager.CONTENT_LIMIT_TYPE_LIST). It is a runtime number, not a constant — different cars allow different counts. The library's compiled-in fallback, used only when the host cannot be reached, is 6. Design for 6, render what the host reports.

How the space is split

  • Blocked wins. The blocked section may take up to 5 rows. It is why you looked.
  • Working always keeps at least one row when anything is working, so “work is happening” is never silently invisible. If there is room for a lane, that row names a lane; if there is not, the row is the counting row and reads +7 more working. It never disappears.
  • An overflowing section spends its last slot on a counting row — title More waiting / More running, secondary text +3 more need input.
  • An empty section is not rendered. Not a heading with nothing under it — nothing at all. The API enforces this anyway: addSectionedList throws on an empty list.

How text is shortened

A row is a title plus at most 2 lines of secondary text (ROW_CONSTRAINTS_FULL_LIST inherits setMaxTextLinesPerRow(2) from ROW_CONSTRAINTS_SIMPLE), and the design guidance caps glanceable text at “1–3 lines and 120 characters”. muxterm's doing string is re-templated on every tool call and can be long. The rule:

  • Collapse all whitespace to single spaces — a doing may contain newlines.
  • Reduce paths to their basename. /home/ken/workspace/muxterm-voice-exit/internal/voice/tools.go → tools.go. The basename is the part a driver can use.
  • Cut at a word boundary at 60 characters and append one ellipsis. With a ~30-character title that lands inside the 120-character glance budget with room to spare.
  • Put the volatile part first. The design guidance is explicit: text meant to be read while driving must be at the beginning of the secondary text, because the host truncates to 2 lines while driving regardless of what you sent.
  • Use one addText call, not two. Two strings are each clamped to one line and each ellipsised separately; a single string is allowed to wrap to the full 2 lines. One call gets more words on screen.

The trap nobody would find until they built it

An Android Auto app may push only 5 templates per task. Exhaust that and the host shows an error and closes your app. A dashboard that redraws when the fleet changes will walk into this within a minute.

Worse in our specific case: the docs also require that the last template in a task be one of six types — Navigation, Pane, Message, MediaPlayback, SignIn, LongMessage. ListTemplate is not one of them. So a one-screen list app cannot even spend its fifth step on the screen it exists to show. Refresh is not an optimisation here; it is the only way the app works at all.

The escape is the refresh rule: a new template of the same type is free if the structure has not changed — same title, same number of sections, same section headers, same number of rows, and the same row titles. Only the secondary text and toggle state may change for free.

So the design above is fast and honest but not free: a lane starting, finishing, or moving from ONGOING to NEEDS MY INPUT changes the row count and the row titles, and costs a step. ConstraintManager.isAppDrivenRefreshEnabled() (Car API 6+) turns list refreshes free and is almost certainly true on any current Android Auto host — but that is an inference, it is queryable at runtime, and the fallback has to be designed, not assumed. Two named fallbacks are in the decision list at the bottom.

D4 · Day and night

Tick Night mode at the top of the page to switch every screen. Now the finding:

The app does not choose either palette. The host switches day/night on its own and picks the light or dark variant of every colour itself, to hold its own contrast ratio. The app is told — CarContext.isDarkMode(), and Session.onCarConfigurationChanged() fires on the switch — but being told is not the same as deciding.

What the app may offer is narrow: four standard CarColors, or up to two custom accents declared in the manifest with light and dark variants. And even those are conditional — “the host may use a default color instead if the colors do not pass the contrast requirements.” Inside a list row, the only text the app may colour at all is the secondary line: Row.Builder.addText honours a ForegroundCarColorSpan, while setTitle accepts only DistanceSpan and DurationSpan and ignores every other span. The row title is not colourable at all.

Therefore: status cannot be carried by colour. Not “should not” — cannot, reliably. It has to be carried by words and by position. That single sentence is why this draft looks the way it does: NEEDS MY INPUT is a literal heading at the literal top, and the voice control says LISTENING in letters rather than turning red.

The two palettes drawn here are a plausible Android Auto rendering, not a specification. A car from a different manufacturer will look different and both will be correct.

What to decide next

Six choices. Each is between named options, and each is genuinely open — this draft picked a side only so there would be something to argue with.

DecisionOptions
1. Voice control (A) action-strip button — the only control that can carry the word LISTENING, costs no row, costs a step to change  |  (B) pinned voice row — state changes are free under the refresh rule, costs one of six rows  |  (C) FAB — biggest target, icon-only, cannot say anything. A and C are mutually exclusive.
Draft leans B, on the grounds that a free state change beats a prettier one.
2. The refresh fallback (i) Trust app-driven refresh — query isAppDrivenRefreshEnabled(), redraw freely, and accept that an old host will close the app  |  (ii) Fixed slots — always render exactly six rows with frozen titles (Lane 1..6) and put the lane label in the secondary text, so nothing ever costs a step  |  (iii) Rate-limit — redraw structure at most once every N seconds and let secondary text carry everything between.
(ii) is ugly and bulletproof. This is the decision with the most engineering consequence.
3. Row order inside a section Longest-waiting first (the lane you have kept waiting)  |  Most-recently-changed first (the lane that just spoke)  |  Stable by lane creation order (rows never move under your eye, which matters at 70mph).
4. What a row title actually is The lane label (“mac remote”)  |  The workspace name  |  The project directory. Labels are auto-generated today and some are poor; if the title is the label, the labels need to be good enough to read at a glance.
5. What a tap on a row does Nothing — rows are inert, everything happens by voice  |  Starts voice with that lane as the subject (“about mac remote…”)  |  Speaks the row aloud. The design guidance says information-only rows are discouraged, which argues against “nothing”.
6. What this is for Personal, DHU + your own phone, never published — then the app category question does not matter  |  Internal test track — then it must declare one of seven categories, none of which fits, and Play's PC-1 criterion is a real risk. See the honesty note below.

One honesty note about shipping

Android Auto has an “unknown sources” developer toggle, and the documentation says plainly that it does not apply to apps built with the Android for Cars App Library. To run in a real vehicle, a templated app must be installed from a trusted source. The Desktop Head Unit is the honest demo path; Internal App Sharing or an internal test track is the honest device path.

And there are exactly seven app categories — NAVIGATION, POI, IOT, WEATHER, MEDIA, MESSAGING, CALLING — one of which must be declared for the host to bind at all. A fleet dashboard is none of them. That does not block a personal build. It does block publishing, and it is better known now than after the UI is finished.
