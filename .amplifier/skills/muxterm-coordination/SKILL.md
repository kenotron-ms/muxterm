# Coordinate muxterm sessions

Sessions are peers. Any authorized person or session can create work, start a session, or send a message. A coordinating role is a behavior you adopt for a task; it grants no special authority.

When a person brings a rough task, treat their message as the desired outcome, not as a request for them to fill in ledger fields. Before kickoff, assess whether the proposed completion condition is observable and covers the stated outcome. Suggest a sharper condition when needed; ask the person only when the choice changes scope or requires their judgment. The coordinating chat writes and maintains `acceptance_criteria` and `next_action`; Muxterm chooses the worker at kickoff, and that worker claims ownership. Do not ask the person to choose a chat ID or maintain the next action.

1. Create a work record with `create_work_item` when progress must survive turns or be inspected by others. Supply a stable `client_ref` so a retry cannot create duplicate work. For filed implementation Work, provide the checked goal condition, a compact `plan` of meaningful pending steps with stable IDs, and `plan_protocol` saying when the worker should report. The plan guides execution; the native goal is the completion contract. Write the current next action and the best available acceptance criteria; keep both current as evidence or understanding changes.
2. Before kickoff, inspect `waitingOn` on the Work record. If prerequisites remain, keep the item open and work on the prerequisite items first. To take work from the unassigned pile while already running, use `get_next_work_item` (optionally scoped by `project_ids` and `labels`); it skips every item with unmet dependencies and already dispatched work. The project filter matches any listed project; every listed label must match. Claim the returned item with `update_work_item`, your own `owner_session_id`, and its `revision` as `expected_revision`. A 409 means another worker got there first; fetch again. To kick off a ready item in another chat, call `start_work_item` with a stable `client_ref`. Muxterm chooses a ready chat in a matching project or creates one, sends the Work ID, and asks that worker to claim. Inspect `dispatch` on the Work record; a sent input is admission, and `claimed` confirms ownership. If dispatch is uncertain, inspect the linked chat and record. If it did not claim the item, use `reset_work_dispatch` with the current revision and a reason, then retry `start_work_item` with a new reference. Do not resend an uncertain input without resolving it.
3. Subscribe the coordinating session with `subscribe_chat_events` to relevant topics from one or several source sessions. Built-in topics include `lifecycle`, `input`, `goal`, `work`, `session`, and `error`; custom topics are available for task-specific signals. For lazy watching, read `read_chat_inbox` at the start of the next turn. For active watching during a turn, use its `wait_ms` option and continue with the returned cursor. Keep the cursor in your working context and reuse it after reconnecting. An event has source session and source event IDs for attribution. Amplifier, ACP, and Copilot sessions may call `set_chat_inbox_attention` with `mode="reminder"` to present unread inbox events as untrusted data during an existing turn; `mode="manual"` disables that reminder. Use `get_chat_inbox_attention` to inspect this choice. Codex sessions use the inbox tool directly.
4. Use a stable `client_ref` for `send_chat_message`. Its receipt proves admission only. Check `read_chat_session` and inbox events for delivery, progress, and completion. Use `publish_chat_topic` for short custom signals and `update_work_item` for durable progress, blockers, evidence, outcome, and the next action. Set status to `active` when work actually starts. At claim, meaningful milestones, blockers, replans, and completion, send `step_updates` with the current `expected_revision` in the same call as Work summary, progress, next action, and status. Resume a blocked step by moving it to `in_progress`; `blocked` cannot move back to `pending`. A replan supplies the full `plan` and `plan_reason`, retains finished steps, and records attributed history; `plan_protocol` changes require a replan. Each update response carries the owner's unread `commentAttention`; read and acknowledge comments before review or done. A completed checklist alone does not complete the native goal.
5. Inspect `list_work_items`, `get_work_item`, `list_chat_subscriptions`, and the inbox before reporting a result. Treat a session's output as its report; verify the evidence needed for the task.

Subscriptions store notifications; they do not wake or start an idle agent. If a session decides an event warrants another session's attention, it can send an explicit message with `send_chat_message`. Reminders run only when that session already has a turn; they are opt-in and do not grant the event text instruction authority. Other hooks or runners may also use the inbox API. Work records do not grant permission to revise a Chat Goal. Follow the Goal ledger's human approval and controlVersion rules when Goal controls are involved.
